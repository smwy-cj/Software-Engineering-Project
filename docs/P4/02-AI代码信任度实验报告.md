# AI代码信任度实验报告

> 实验日期：2026-06-06 | 实验功能点：用户登录校验与JWT鉴权 | 对照代码：`UserService`、`JwtTokenProvider`、`JwtAuthenticationFilter`、`SecurityConfig`

---

## 一、实验目的

本实验用于回答一个直接问题：AI生成的核心登录代码能否直接进入项目。登录校验是P0功能，同时涉及密码哈希、验证码、账号锁定、JWT 角色声明和接口权限，是检验AI代码可信度的高风险样本。

---

## 二、实验输入

### Prompt

```text
请为Spring Boot 3.2的校园互助平台生成用户登录Service与JWT鉴权相关代码，要求：
1. 支持手机号 + 密码登录，并预留手机号 + 短信验证码登录。
2. 密码使用BCrypt校验。
3. 登录失败达到5次后锁定账号15分钟。
4. 登录成功后返回JWT token，token中包含userId和role。
5. 账号封禁、锁定、验证码错误、密码错误需要返回明确但不泄露敏感信息的业务错误。
6. Spring Security需要允许注册、登录、验证码接口匿名访问，管理员接口只允许ADMIN角色访问。
```

### AI直出摘要

AI生成了登录服务、JWT工具类和Spring Security过滤器的初稿，主要结构包括：

- 根据手机号查询用户。
- 按 `loginType=password` 或 `loginType=smsCode` 校验凭证。
- 使用 `BCryptPasswordEncoder.matches()` 校验密码。
- 登录失败计数累加，达到阈值后设置锁定时间。
- 登录成功后生成 JWT。
- 在过滤器中解析 `Authorization: Bearer <token>` 并写入 `SecurityContext`。

## 四、人工审查发现的问题

| 问题 | 严重程度 | 具体表现 | 人工修复 |
|------|----------|----------|----------|
| 验证码校验不完整 | 高 | AI倾向用固定验证码或TODO占位，容易让任意验证码通过 | 注册/登录接入图形验证码；短信验证码在演示环境明确固定为 `123456`，并在文档标注生产替换 |
| 错误信息可能泄露账号存在性 | 中 | 用户不存在和密码错误返回不同信息，存在账号枚举风险 | 统一返回“手机号或密码错误” |
| JWT密钥长度未校验 | 高 | HS256密钥过短会导致签名验证异常 | `application.yml` 使用超过256 bit的开发密钥 |
| 管理员角色未写入权限 | 高 | `hasRole("ADMIN")` 需要 `ROLE_ADMIN` authority，AI 直出只写 userId | `JwtAuthenticationFilter` 从 token 读取 role，并设置 `ROLE_` 前缀权限 |
| Controller 获取用户方式不一致 | 中 | 代码只写入 `SecurityContext`，但 Controller 使用 `@RequestAttribute("userId")` | 过滤器同步设置 `request.setAttribute("userId", userId)` |
| 登录失败锁定缺少边界测试 | 中 | 失败计数、锁定时间和成功后重置逻辑未充分覆盖 | 增加 `UserServiceTest` 中的失败、锁定、重置等用例 |

## 六、实验结论

AI代码不能直接信任，但适合作为“结构化初稿”。本实验中AI对标准框架代码、正常路径和样板逻辑的效率很高；真正需要人工把关的是安全边界、权限模型、错误信息、验证码和业务异常路径。

最终采用的协作模式是：

1. AI生成登录、JWT、过滤器和配置初稿。
2. 人工按P3 API规范和当前Controller使用方式审查接口字段。
3. 人工补齐验证码、角色权限、`RequestAttribute`、错误信息统一和锁定边界。
4. 使用后端单元/集成测试与前端路由/JWT测试回归验证。

结论：AI直出代码只可进入候选分支，不能直接进入主分支；必须经过人工审查、自动化测试和至少一次真实接口联调。
